# XP — Design Spec

Date: 2026-08-02
Status: approved, ready for implementation plan

---

## Problem

XP is a promise the app cannot keep.

`UserModel.xp` defaults to `0`, is read in exactly two places, and **nothing anywhere
increments it** — there is no `$inc` on it in the entire API. So every user permanently
sees a chip reading "Start Collecting" on Today and "Start collecting XP" on Profile,
inviting them to collect something that can never be collected. That ships today.

`AGENTS.md` never mentions XP or gamification. It was invented in the UI with no product
definition behind it, so this spec is defining it rather than recovering it.

## Solution

A lifetime record of effort, awarded per action as it happens, stored as an append-only
ledger whose idempotence comes from a unique index rather than from careful code.

---

## Decisions

| Question | Decision | Why |
|---|---|---|
| What XP *is* | A record of effort, never a score | No levels, no thresholds, no targets, nothing to fall short of. There is no state of this number that can read as a scolding, which is the bar this codebase already sets for itself. |
| When it is awarded | Per action, at the moment it happens | The number moves while you are watching — the one moment `HabitCard` already calls "worth celebrating". |
| Storage | An append-only ledger, one row per award | A double-award is invisible: nobody notices they got 20 instead of 10. Idempotence has to be structural. |
| Revocation | Never | Uncheck a habit and the XP stays. You did it; the record says so. |

### The voice this has to survive

> `HabitCard.tsx` — *"A zero streak is a beginning, not a failure. '0D Streak' reads as a scolding."*
> `ai/synitheia.ts` — *"State the pattern; the judgement is theirs to make."*

XP must never acquire a tone this product refuses everywhere else. That is why there are
no levels and no targets: a number you can only add to cannot be behind.

## What earns XP

| Award | XP | Once per |
|---|---|---|
| Habit completed | 5 | habit, per day |
| Every habit scheduled that day completed | 10 | day |
| Water target reached | 5 | day |
| Habit streak reaches 7 / 30 / 100 | 25 / 100 / 250 | habit, per milestone, ever |
| Month closed within budget | 100 | month |

**Flat per habit, not scaled by difficulty.** Habits carry a measure — steps, minutes, a
count, a plain check — and paying more for a "harder" one only invites people to edit
their own targets downward. Ten easy habits earning more than two hard ones is fine: they
did ten things.

**The day bonus is the counterweight.** It is the only award that gets *harder* as habits
are added, which stops the flat per-habit rate from rewarding habit-hoarding.

**Calories are deliberately excluded.** The award would have to mean "within a range"
rather than "reached a number", and that is a judgement about food this app is otherwise
careful not to make. Water has an unambiguous direction; calories do not.

**Logging is never paid.** No XP for an expense row, a water glass, or a meal entry.
Paying for logging is what turns a record of effort into a reason to log noise — six
100ml waters would beat one 600ml.

### Explicitly out of scope

- Levels, thresholds, unlocks, or any target derived from XP.
- Leaderboards or any comparison to another person.
- Backfilling existing users from their history. See "Known consequence" below.

## The ledger

A new `XpAward` collection. One row per award:

```
userId    ObjectId
key       string    the dedupe key — unique together with userId
amount    number    integer, positive
awardedAt Date
```

`{ userId, key }` carries a **unique index**. Every write is an upsert-or-fail against
it, so a replayed tap, an optimistic retry, or an offline sync collides and becomes a
no-op. Idempotent because the database refuses, not because the code remembered.

### Dedupe keys

```
habit:<habitId>:<localDate>        a habit completed that day
day:<localDate>                    every habit scheduled that day completed
water:<localDate>                  water target reached that day
streak:<habitId>:<milestone>       a streak milestone, once ever
budget:<YYYY-MM>                   a month closed within budget
```

Every key is derived from a `LocalDate` in the user's own timezone, never from the
server's clock — the same rule the rest of this codebase follows.

### The cached total

`user.xp` stays, as a **cache** of the ledger's sum. It is incremented **only when the
insert actually happened** — a duplicate key means no award and no increment.

This codebase has a standing lesson about caches:

> `context/aggregator.ts` — *"a cache nobody invalidates is just a wrong answer with good latency"*
> `nutrition/service.ts` — *"The tempting alternative — `$inc` the totals by the delta on each write — drifts."*

The ledger is the truth and the total is recomputable from it, so drift is detectable and
fixable rather than permanent. That is the difference between this and incrementing a bare
counter.

## Where awards fire

| Award | Site |
|---|---|
| Habit completed, day complete, streak milestone | `habits/service.ts` `logHabit`, after `recomputeStreak` |
| Water target reached | `water/routes.ts` `createEntry`, after the day total is read back |
| Month within budget | `today/routes.ts`, lazily on the first load of a new month |

The month award has no scheduler because **nothing in this app runs on a schedule**. It
follows the existing pattern: `postDueSubscriptions` and `runDetectors` both do lazy
month/day work on a Today load. The award is granted for the *previous* month, only if a
`monthlyBudgetMinor` is actually set, and only once — the `budget:<YYYY-MM>` key enforces
that even if Today is loaded fifty times.

No budget set means no award and no penalty. A month over budget means no award — never a
deduction, and never a message about it.

---

## Awards are computed, not scattered

The decision of *what* an action earns lives in one pure function in
`@synitheia/shared`, not spread across three service files:

```ts
awardsForHabitLog(input): XpAward[]
awardsForWaterEntry(input): XpAward[]
awardForMonth(input): XpAward | null
```

Each returns keys and amounts. The services only persist what they are handed. This keeps
the rules unit-testable without Mongo, and keeps the amounts in one place where they can
be read at a glance rather than reverse-engineered from three call sites.

## Known consequence: existing users start at zero

Nobody is backfilled. A user with a month of real history opens the app after this ships
and still sees 0 XP, then watches it start moving.

Backfilling from existing `HabitLog` documents would be *reading* history rather than
inventing it, and is genuinely defensible. It is out of scope for v1 because it is a
migration with its own failure modes, and because the honest version of this feature does
not need it to be correct. It is recorded as a follow-up rather than pretended away.

## Testing

- **The award rules** — pure, in `@synitheia/shared`, unit-tested. Every award, every key
  shape, and the boundaries: a streak of 6 versus 7, a water total one millilitre under
  target, a day where nothing was scheduled.
- **Idempotence** — the property this feature turns on. Award the same action twice
  through the real service against the in-memory replica set and assert the ledger has one
  row and the total moved once. Do this for every award site, not just the helper.
- **Never revoked** — complete a habit, un-complete it, complete it again; assert the
  total is unchanged after the second and third steps.
- **Timezone** — a habit completed at 23:30 in `Asia/Kolkata` must key to the user's local
  date, not the server's.

There is no React Native component test infrastructure and this spec does not add one, so
the chip's appearance is a device-pass item rather than a test.
